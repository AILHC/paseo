# Paseo v0.1.96 升级验收清单

## 验收目标

本清单用于验收当前全局 `paseo` link（全局命令链接）已切到升级 worktree（独立工作树）后的真实使用效果。

当前状态：

- 全局 `paseo` 已指向 `.worktrees/paseo-upgrade/packages/cli`。
- CLI（命令行工具）版本应为 `0.1.96`。
- 升级分支为 `codex/paseo-v0.1.96-upgrade`。
- 候选提交为 `adcbe34e`。
- 本轮更新到 `v0.1.96` 未启动或重启真实 daemon（守护进程）；daemon 实际运行状态以验收时 `paseo daemon status` 为准。
- 父仓库 `vendor/paseo` gitlink（子模块指针）尚未更新。

验收结论用于决定是否把候选提交合回 Paseo `custom/main` 并更新父仓库 `vendor/paseo` 指针。

## 升级变更面

本次从本地基底 `v0.1.85-9-g2048ca8f` 升到官方 `v0.1.96`，重点影响这些区域：

| 变更面                                            | 可能影响                                                                                                   |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| daemon 启动与状态管理                             | 真实 daemon 是否能从旧数据目录 `C:\Users\AILHC\.paseo` 正常启动；旧会话是否可读                            |
| agent/session（智能体/会话）列表                  | 旧 agent 展示、idle/running 状态、归档状态、列表刷新                                                       |
| session import（会话导入）                        | 上游把旧 persisted session（已持久化会话）枚举接口迁移为 `listImportableSessions` / `importSession`        |
| Codex provider（Codex 提供方）                    | thread list（线程列表）、archived thread（已归档线程）、cwd（当前工作目录）过滤、compact（上下文压缩）兼容 |
| Claude provider（Claude 提供方）                  | 环境变量、模型/思考强度配置，尤其本地 `xhigh -> max` 兼容                                                  |
| MCP（Model Context Protocol，模型上下文协议）工具 | `create_agent`、`update_agent`、内部 Paseo MCP 注入、agent labels（标签）更新                              |
| archive（归档）语义                               | 上游默认归档行为与本地定制的显式 `/archive-session` 入口冲突，需要重点验收                                 |
| workspace/tab（工作区/标签页）                    | 关闭 agent tab 不应归档；terminal tab 仍应可关闭                                                           |
| desktop/web UI（桌面/网页界面）                   | 连接 daemon、工作区列表、agent tab、terminal tab、文件预览                                                 |
| CLI 命令                                          | 全局命令是否使用 `0.1.96`；`agent`、`provider`、`daemon` 子命令是否正常                                    |

## 本地定制必须保留的语义

这些是本地 fork（分叉版本）相对官方 Paseo 的定制点，验收时优先级最高：

- 关闭 agent tab 不会隐式归档 agent。
- `archive_agent_request` 不直接归档 agent，应提示使用 `/archive-session`。
- `close_items_request` 对 agent ids（智能体 ID）是 no-op（无操作），但仍能关闭 terminal（终端）。
- 只有用户显式发送 `/archive-session` 才归档当前 agent session。
- native archived sync（原生归档状态同步）仍能把 Codex 原生 archived thread 映射到 Paseo 已存储 agent。
- native unarchive（原生取消归档）仍可恢复被原生归档的会话。
- internal Paseo MCP server（内部 Paseo 模型上下文协议服务）只注入 provider launch config（提供方启动配置），不污染用户可见 stored config（已存储配置）。
- MCP `update_agent` 同时更新 name（名称）和 labels（标签），并且 live agent（运行中智能体）内存状态与存储状态一致。

### 3. 旧会话与旧 agent 可见

目的：确认升级后不会丢失或隐藏旧数据。

步骤：

1. 执行：

   ```powershell
   paseo agent ls
   ```

2. 打开平时使用的 Paseo UI（用户界面）。
3. 检查旧 workspace（工作区）、旧 agent、旧 idle session（空闲会话）是否可见。

预期：

- 旧 agent 数量大体符合升级前状态。
- 旧 idle agent 能打开。
- 打开旧 agent 不触发自动归档或异常状态切换。

失败判定：

- 旧 agent 列表为空。
- 大量旧 agent 消失。
- 打开旧 agent 后报错或被自动归档。

验收记录：

```text
结果：失败
记录时间：2026-06-11
测试会话 ID：874c3500-9695-4353-a16a-b2915674e085
关联 Codex thread：019e7301-8613-7df0-a241-8e701350d16c
```

实际现象：

- 在 agent 内输入 `/archive-session` 后，UI 没有立刻显示归档状态。
- session 列表没有立刻显示该会话已归档。
- 刷新网页后，session 列表才显示该会话归档状态正确。
- 刷新后点击打开该已归档会话，一直打不开。
- 刷新网页后，所有未归档会话都出现在 tab 栏。

当前证据：

- Paseo 存储记录 `C:\Users\AILHC\.paseo\agents\F-projs_space-ai-ai-workflow-lab\874c3500-9695-4353-a16a-b2915674e085.json` 中已有 `archivedAt`，说明后端持久化归档状态成功。
- daemon 日志显示点击打开该归档会话时，后端尝试 resume（恢复）Codex 原生 thread：

  ```text
  Failed to resume Codex thread 019e7301-8613-7df0-a241-8e701350d16c:
  session 019e7301-8613-7df0-a241-8e701350d16c is archived.
  Run `codex unarchive 019e7301-8613-7df0-a241-8e701350d16c` to unarchive it first.
  ```

- 相关后端路径：
  - `packages/server/src/server/agent/agent-loading.ts` 的 `ensureAgentLoaded` 对 stored agent（已存储智能体）没有区分 `archivedAt`，会直接调用 `resumeAgentFromPersistence`。
  - 对 Codex archived thread（已归档线程）而言，普通 resume 会被 Codex app-server 拒绝。
- 相关前端路径：
  - `packages/app/src/workspace-tabs/agent-visibility.ts` 会把当前 workspace（工作区）下所有未归档 agent 放入 `activeAgentIds`。
  - 同文件会把满足 `shouldAutoOpenAgentTab(agent)` 的未归档 agent 放入 `autoOpenAgentIds`。
  - `packages/app/src/stores/workspace-layout-actions.ts` 的 `addMissingEntityTabs` 会把 `autoOpenAgentIds` 中缺失的 agent tab 自动加入 tab 栏。

初步分析：

- “刷新后归档状态才正确”说明归档持久化成功，但实时 UI 状态同步或 tab reconciliation（标签页调和）没有即时反映归档结果。
- “已归档会话打不开”更像是打开路径错误：归档会话点击后不应直接走普通 provider resume，至少需要先走 unarchive（取消归档）路径，或显示 archived detail（归档详情）并提供恢复按钮。
- “刷新后所有未归档会话都出现在 tab 栏”更像是前端 auto-open 策略过宽：`autoOpenAgentIds` 被构造成当前 workspace 下所有符合自动打开条件的未归档 agent，刷新后的 `reconcileTabs` 会把它们补齐到 tab 栏。

待验证假设：

1. `archiveSession` 归档 live agent（运行中智能体）后，发出的 `agent_update` / `agent_archived` 事件不足以让前端 session store（会话状态存储）和 workspace tabs store（工作区标签状态存储）同步关闭或移除该 tab。
2. archived stored agent 的 timeline fetch（时间线获取）触发了 `ensureAgentLoaded`，该函数没有 archived 分支，导致错误 resume Codex archived thread。
3. `shouldAutoOpenAgentTab` 或其上游输入在刷新后把历史未归档根 agent 全部视为应自动打开，导致 tab 栏膨胀。

是否阻塞切换 `vendor/paseo`：是。

建议处理优先级：

- P0：修复归档会话点击打开路径，避免 archived Codex thread 被普通 resume。
- P0：修复 `/archive-session` 后实时 UI 状态同步，归档后应立即从普通 session 列表/活动 tab 中消失或显示 archived 状态。
- P1：修复刷新后 tab 自动补齐策略，避免把所有未归档会话自动打开到 tab 栏。

待统一对齐的修复方向：

1. 点击打开已归档会话时，自动解除 Codex 原生归档，再继续打开会话；该行为需要保证幂等，且不能误解除非当前用户主动打开的归档 thread（线程）。
2. 修复 `/archive-session` 的实时 UI 同步：命令执行成功后，session（会话）列表、当前 tab（标签页）和 agent 状态应立即反映归档结果，不能依赖刷新网页。
3. 修复 tab 栏刷新恢复策略：刷新后只恢复用户当前打开或应保留的 tab，不应把 workspace（工作区）内所有未归档会话都自动塞进 tab 栏。

当前归因分层：

- 已归档会话点击打不开：主因偏 Paseo v0.1.96 上游 archived agent（已归档智能体）进入普通 resume（恢复）路径的缺口；本地定制需要补齐升级后的兼容闭环。
- `/archive-session` 后 UI 不即时变化：偏本地定制集成问题，需要修事件广播、store（状态存储）更新或 tab reconciliation（标签页调和）联动。
- 刷新后所有未归档会话进入 tab 栏：偏升级后的前端 tab 自动恢复策略问题，需要和旧版本行为对比后收窄 auto-open（自动打开）规则。

- UI provider 选择和 CLI provider 列表一致。

失败判定：

- provider 列表卡住或整体报错。
- 一个未配置 provider 导致其他 provider 不可用。
- UI 与 CLI 展示不一致，导致用户选择错误 provider。

### 16. timeline 同步与恢复

目的：覆盖上游 timeline（时间线）同步变化，确认旧会话、导入会话、新会话的消息流都能正确显示。

步骤：

1. 打开一个升级前已存在的旧 agent。
2. 打开一个新建 agent。
3. 打开一个通过 import session（导入会话）得到的 agent。
4. 对每类 agent 检查历史消息、最新消息、发送中状态和刷新后的顺序。

预期：

- 历史消息不丢失。
- 新消息能实时追加。
- 刷新后消息顺序稳定。
- loading（加载中）状态不会永久停留。

失败判定：

- timeline 空白但后端实际有消息。
- 消息顺序反转或重复。
- 刷新后最新消息消失。
- 打开 archived agent（已归档智能体）时错误触发普通 resume（恢复）路径。

### 17. 文件预览

目的：覆盖上游文件预览变化，确认 agent 产物和 workspace 文件能在 UI 中正常打开。

步骤：

1. 选择一个已存在的文本文件、Markdown 文件和较小图片文件。
2. 从 UI 文件入口或 agent 引用中打开预览。
3. 在预览打开后切换 tab，再返回原预览。

预期：

- 文本和 Markdown 内容可读。
- 图片能加载，不显示空白。
- 预览不会阻塞 agent tab 或 terminal tab。
- 切换 tab 后预览状态合理保持或可重新打开。

失败判定：

- 文件预览空白。
- 预览导致 UI 卡死。
- 文件路径包含中文或空格时打不开。

### 18. desktop 多窗口

目的：覆盖上游 desktop（桌面端）多窗口变化，确认多个窗口不会互相污染 tab、workspace 或连接状态。

步骤：

1. 打开桌面端第一个窗口，连接真实 daemon。
2. 再打开第二个桌面窗口。
3. 两个窗口分别打开不同 workspace 或不同 agent tab。
4. 在一个窗口关闭 tab，观察另一个窗口。

预期：

- 两个窗口都能连接 daemon。
- 一个窗口的 tab 操作不会错误关闭另一个窗口的 tab。
- workspace 选择、agent 列表和连接状态不会互相错乱。

失败判定：

- 第二个窗口无法连接。
- 一个窗口关闭 tab 导致另一个窗口状态异常。
- 多窗口下出现重复自动打开大量 agent tab。
